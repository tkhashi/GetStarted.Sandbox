# Specify Sample 憲章

## コア原則

### I. コード品質と保守性
すべての変更は、lint/format/静的解析を警告ゼロで通過しなければならない。
公開 API は、適用可能な場合に明確な使用例を含むドキュメントを必須とする。
エラー処理は明示的かつ観測可能でなければならず、黙って失敗してはならない。
重複ロジックはリファクタリングするか、PR で明確に正当化しなければならない。

### II. テスト標準（非交渉）
すべての振る舞い変更には、新規または変更された挙動をカバーするテストを含めること。
バグ修正には、修正前に失敗し修正後に成功する回帰テストを必ず追加すること。
テストは CI で実行され、決定的でなければならない。フレークは失敗扱いとする。
テスト範囲はリスクに応じること（ロジックは単体、境界は統合テスト）。

### III. UX 一貫性とアクセシビリティ
UI 変更は、承認されたデザインシステムのコンポーネント・トークン・パターンを使用すること。
デザインシステムからの逸脱は、レビューで記録し承認を得ること。
新規または変更された UI は、キーボード操作・コントラスト・ラベルにおいて
WCAG 2.1 AA を満たさなければならない。
ユーザー向け文言は、プロジェクトのスタイルガイドと用語に従うこと。

### IV. パフォーマンス予算と検証
各機能は、計測可能なパフォーマンス予算（例: レイテンシ、
スループット、メモリ、バンドルサイズ、フレームレート）を plan に定義すること。
変更には、予算を満たすことを示すベンチマークまたはプロファイル証拠を含めること。
予算超過の回帰は、是正または明示的な承認と計画が必要である。

### V. 変更安全性とレビュー規律
すべての変更は、マージ前にコードレビューを必須とする。高リスク変更は
2 名以上の承認または指定レビュワーを要求する。
CI は、lint・テスト・パフォーマンス検証がすべて成功していること。
破壊的変更は、移行計画とバージョニング更新を必須とする。

## 品質ゲート

- lint/format/静的解析が警告ゼロであること
- 必要テストが追加され、CI がグリーンであること
- UI 変更時は UX 一貫性レビューが完了していること
- パフォーマンス予算が定義され、検証されていること
- 例外は明示的な承認付きで文書化されていること

## 開発ワークフロー

- 実装前に spec と plan を作成すること
- 変更は小さくレビュー可能な単位で提供し、ロールバック経路を明確にすること
- 公開 API とユーザー向け変更はドキュメント更新を必須とする
- リリースノートに破壊的変更と性能影響を記載すること

## ガバナンス

- 本憲章は他の開発ガイダンスに優先する
- 改定には、文書化・理由・バージョン更新が必要
- バージョニングはガバナンス変更のためのセマンティックバージョンに従う
- 遵守はすべての PR とリリースチェックリストで確認する
